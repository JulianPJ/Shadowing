# Accounts and learner sync

Core practice needs no account. Anonymous learner data stays in the browser. Signed-in learners also sync eligible learner state to D1, the production application database. Auth is **Better Auth 1.7.7**, pinned in `package.json`.

## Authentication

Better Auth owns:

- password hashing (scrypt);
- verification and reset tokens;
- Google OAuth state and PKCE;
- identity linking;
- sessions and cookie signatures.

**Email sign-up**

- Email registration requires verification. Saving words and sync also require a verified email. An unverified account sees "Verify your email…" with **Resend verification email** under Profile → Account.
- Passwords are 12–128 characters. A password reset revokes existing sessions.
- Email goes through Resend with a 10-second timeout. Without a mail transport, registration and reset fail with an explicit 503, so no unusable password account is created.

**Google**

- Google uses the authorization-code flow without offline access.
- Implicit same-email linking is **disabled**. To link, sign in with the existing method, then choose **Connect Google** from the account section.
- Different emails cannot link, and an identity that already belongs to another user cannot merge accounts.
- Business logic uses only `session.user.id`.

**Sessions**

- Sessions last 14 days and rotate daily. Cookies are HttpOnly, SameSite=Lax, and Secure on HTTPS.
- Cookie caching is off, so data endpoints validate the database session on every request. No session or OAuth token is stored in localStorage.
- Better Auth's database-backed rate limits are on, keyed by `cf-connecting-ip`.
- Auth logging is off, so provider errors cannot leak credentials.

**Return paths.** Return paths (`callbackURL`, `redirectTo` and similar) must be same-origin learning pages. `safeReturnPath` in `src/lib/auth/return-path.ts` holds the list; anything else returns 400.

**Worker routing.** The Worker (`cloudflare-worker.js`) intercepts `/api/auth/*`, `/api/account/*` and `/api/sync/*` before vinext. It builds a request-local auth instance with the native `HIBIKI_DB` binding, the origin and the secrets, so no singleton ever holds one request's secrets.

**Runtime check.** `scripts/check-d1-runtime.mjs` runs the production bundle in workerd with native D1. It covers registration, verification email through mocked egress, the session cookie, a sync write and sign-out.

## Schema

`0002_auth.sql` holds the framework tables (`user`, `account`, `session`, `verification`, `rateLimit`). It was generated by `scripts/generate-auth-migration.ts`. Never rewrite an applied migration.

| Migration | Adds |
| --- | --- |
| `0003_user_sync` | Preferences, lessons, practice sessions, quiz attempts, bookmarks, difficulty references, practice archives |
| `0004`, `0008` | Saved words (`user_dictionary_entries`), with cursor paging |
| `0005`, `0006` | Plan access and test accounts |
| `0007`, `0011` | Review cards and rating history (`user_review_states`, `user_review_events`) |
| `0009`, `0013` | Word statuses (`user_word_knowledge`) and the `synced_at` watermark |
| `0010` | Review limits in preferences |
| `0012` | Discover preferences, feedback, events and Watch later |

The deck, membership and tag tables from `0007` and `0008` stay in D1 unused ([vocabulary](vocabulary.md)).

Every application row has a queryable `user_id`, with a foreign key to `user.id` and cascade deletion. Composite primary keys give owner-scoped reads and idempotent upserts.

## API

| Endpoint | Behaviour |
| --- | --- |
| `GET /api/account/me` | Identity and configured sign-in methods; never session or token fields |
| `GET /api/sync/bootstrap?cursor=…` | Up to 50 rows from one collection plus preferences, with a keyset cursor |
| `POST /api/sync/push` | 512 KB streaming limit; at most 50 records per collection; strict validation |
| `GET /api/sync/lesson?id=…` | Restores a public YouTube lesson from matching trusted captions; 404 when the media must be reattached |
| `/api/dictionary`, `/api/review`, `/api/knowledge` | Saved words, review cards and word statuses |
| `/api/discover/*`, `/api/watch-later` | Discover preferences and events, and Watch later |

**Request rules**

- Ownership always comes from the validated session. A browser-supplied `userId` is rejected.
- Each request carries an expected-account header. A mismatch returns 409, so a stale tab cannot upload a previous account's cache.
- Writes require the configured origin and a JSON Content-Type.
- Responses are `no-store`. An unauthenticated request returns 401; an unavailable database returns a retryable error.

**Quiz scoring.** Quiz attempts sync the selected answers and results, **never evidence quotes**.

- When the trusted quiz is in `generated_artifacts` (or is the authored demo), the server recomputes the score.
- Otherwise the attempt is stored with `verified=false`.

## Local-first sync

Every change is written locally first. Playback never waits for the network.

**Learner sync** (`src/lib/sync/client.ts`) covers progress, sessions, attempts, bookmarks, preferences and difficulty.

- A change is debounced by 1.5 s, then only changed records are pushed, 20 at a time.
- Retry state is persisted before each request.
- Focus, reconnect and the minute poll reuse a full sync from the last 5 minutes unless local changes are pending.

**Channel engine.** Review, word statuses and Discover share `src/lib/sync/channel.ts`.

- Each owner has one sync in flight, plus one queued rerun.
- A channel reuses a sync from the last 5 minutes unless it has pending work or the account changed.
- Signed-out and unverified accounts are skipped.
- `navigator.locks` keeps review writes to one tab at a time.
- Shared triggers: account change (forced); reconnect, focus, hydration and a 60 s poll (routine).

**Incremental pulls.** Word statuses pull incrementally by `synced_at`, with a 60 s overlap. The watermark advances only after the records are stored locally. A push response returns the stored records, so the local copy matches the winner.

**Status in the UI.** Sync is silent. The only notice is "Your session expired" (with a sign-in button) after a 401; other failures retry in the background.

**Local keys.** Anonymous keys are `hibiki:v1:*`. Account keys live under `hibiki:v1:account:<userId>:`.

- The persisted `active-account` value only selects a cache. It is **not authentication**.
- Sign-out restores the anonymous keys.
- Lesson, transcript and translation caches stay on the device.

**First sign-in.** On the first sign-in with anonymous state, Hibiki asks **"Add this device's Hibiki progress to your account?"**

- A compact snapshot is frozen locally and is never pushed before the learner accepts.
- Accepting merges eligible records by stable IDs, so a retry is idempotent.
- Declining keeps the anonymous data local.
- Neither choice deletes local history.

## Merge rules

| Record | Rule |
| --- | --- |
| Preferences | Latest `updatedAt` wins; undated preferences cannot overwrite dated ones. Fields an older client omits survive. |
| Bookmarks | Union by lesson, transcript and section; the latest state wins; deletion wins ties |
| Practice sessions | Immutable UUID; the latest valid version wins, never summed |
| Quiz attempts | Immutable ID; the latest version wins; retakes stay separate |
| Completion | Monotonic for the same transcript revision |
| Last position | Latest date for the same transcript revision only |
| Difficulty | Latest `generatedAt` |
| Imported archives | First insertion wins |
| Review cards | Versioned. A conflicting edit restores the server schedule and shows a one-line notice. |
| Word statuses | Last writer wins by `updatedAt` |

Incoming dates more than five minutes in the future are rejected. A record cannot change its lesson or revision.

## Privacy

**Synced metadata**

- lesson title and author, stable identities, duration, last position;
- practice dates, completion and active time;
- section replay, reveal and recording **counts**;
- quiz answers and results, bookmarks, compact difficulty;
- saved words with their sentence, review state and word statuses.

**Never leaves the browser**

- recordings and media bytes;
- object URLs and local paths;
- signed URLs and Vimeo access hashes;
- the translation cache;
- imported or pasted transcript text;
- private quiz evidence and Whisper inputs.

Metadata that contains a URL or local path is rejected. The one exception is a page lesson's own page URL ([Hibiki Bridge](browser-extension.md)).

**On another device**

- Public YouTube lessons restore when a trusted transcript matches.
- Direct, Vimeo, local and page lessons need their media again; their learning history is still there.

## Production setup

- **Origin:** `https://hibikiapp.net`. The former `workers.dev` hostname redirects browser visits to this origin; existing login cookies do not migrate between hosts.
- **Google redirect URI:** `https://hibikiapp.net/api/auth/callback/google`. Add it to the Google OAuth client before deploying this canonical-origin change. For local OAuth, add `http://localhost:3000` and its callback.
- **Secret names:** `AUTH_SECRET` (stable, at least 32 random characters), `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `RESEND_API_KEY`, `AUTH_EMAIL_FROM`.
- **`AUTH_BASE_URL`** and **`AUTH_EMAIL_FROM`** are plain-text bindings in `cloudflare.config.ts`; `RESEND_API_KEY` is a secret binding.
- Set secrets with the cf CLI or the dashboard, never Git or chat.
- Verify `hibikiapp.net` in Resend; configure the sending API key securely on the `shadowing` Worker. Sender: `Hibiki <accounts@hibikiapp.net>`.
- Ensure `hibikiapp.net` routes to the `shadowing` Worker before switching the canonical origin; keep the relay URL and shared token unchanged.
- After deployment, test email verification, password reset and Google sign-in on `hibikiapp.net`, then reload Hibiki Bridge and check its production origin setting.

**Release order**

1. Commit migrations.
2. `npm run deploy` (applies D1 migrations, then deploys the prebuilt Worker).
3. Smoke-test real email, Google and two devices.

Never reset D1. A mocked test is not evidence of a real Google callback.

**Tests**

- `tests/accounts-sync.test.ts` covers local D1 auth, sessions, user isolation, malicious ownership, OAuth state and linking, score recomputation, conflicts and paging.
- `tests/e2e/accounts.spec.ts` covers import and decline, privacy exclusions, two browser devices and offline practice. It uses a mocked account transport.
- CI never contacts Google or sends email.
